# AI Coding Assistant Prompt

## Mission

Implement a smart-batching GPS ingest pipeline with a dual-path filter gate that separates PostgreSQL as the operational truth store from Hyperledger Fabric as the compliance audit layer. The system must reduce Fabric writes by 96%+ while preserving 100% critical-event auditability.

Reference the growth plan at `@/sec/root/SHFTCCONK/skene-context/growth-plan.md` for additional product and business context before proceeding.

## What We're Building

1. **PWA IndexedDB ping buffer** with four flush triggers (count, time, session-end, network-recovery) and exponential backoff retry
2. **Batch ingest endpoint** with idempotency, bulk PostgreSQL INSERT, and post-commit ledger classifier
3. **Dual-path filter gate**: displacement threshold (250m), status-change detector, and 15-minute heartbeat scheduler
4. **Upstash worker** that builds Merkle-rooted Fabric transactions from classified batches, maintaining a vehicle-level hash chain
5. **Compliance panel SSE stream** surfacing verified anchor count vs raw pings with loss-aversion upgrade gate at 500 anchors + Day 28

## Technical Tasks — Implement in This Order

### Task 1 — PWA Buffer + Flush Logic
**File:** `apps/driver-pwa/src/lib/gps/buffer.ts`

- Use IndexedDB as the persistence layer so unsynced pings survive tab kills and offline periods up to 72 hours
- Implement all four flush triggers:
  - `unsynced ping count >= 12`
  - `90 seconds elapsed`
  - `visibilitychange` or `beforeunload` events fire
  - `navigator.online` fires after an offline period
- Implement exponential backoff retry on failed flush attempts
- Guarantee zero ping loss across all flush scenarios

### Task 2 — Batch Ingest Endpoint with Idempotency + Bulk INSERT
**File:** `src/routes/api/v1/pings/batch/+server.ts`

- Accept batched ping payloads from the PWA
- Enforce idempotency using a client-generated batch UUID (deduplicate on re-delivery)
- Execute a single bulk `INSERT` into PostgreSQL for all pings in the batch
- After commit, invoke `classifyForLedger` (Task 3) on the batch
- Wire genesis automation (Task 7) synchronously within this handler post-classification

### Task 3 — Ledger Classifier
**File:** `src/lib/server/ledger/classifier.ts`

Implement `classifyForLedger(batch)` with three write triggers:

| Trigger | Condition |
|---|---|
| Displacement | Haversine distance >= 250m from last anchor position |
| Status-change | Any ping in batch carries `trip_start`, `trip_end`, `speed_anomaly`, `route_deviation`, or `offline_recovery` |
| Heartbeat | 15-minute scheduled job fires with no prior ledger write in window |

- Return a structured result including `trigger_reason` (values: `'displacement'`, `'status_change'`, `'heartbeat'`, `'genesis'`, `null`)
- `trigger_reason === 'genesis'` fires when no `vehicle_ledger_anchor_state` row exists for the vehicle
- Status-change events must **unconditionally** produce a ledger write — no threshold check applies

### Task 4 — Database Schema Migration
**File:** `supabase/migrations/YYYYMMDD_ledger_schema.sql`

Create two tables:

**`vehicle_ledger_anchor_state`**
- Tracks per-vehicle last anchor position, timestamp, hash chain tip, and anchor count
- Used by classifier to compute displacement and detect genesis condition

**`vehicle_ledger_jobs`**
- Job queue consumed by the Upstash worker
- Columns: job ID, vehicle ID, batch reference, trigger reason, Merkle root, Fabric tx ID, status, created/completed timestamps

Include appropriate indexes for vehicle ID lookups and job status polling.

### Task 5 — Upstash Ledger Worker
**File:** `src/lib/server/workers/ledger-inscription.ts`

- Poll or consume `vehicle_ledger_jobs` for pending jobs
- For each job:
  1. Fetch the ping batch from PostgreSQL
  2. Compute a Merkle root over the ping payload hashes
  3. Link to the previous anchor hash (hash chain continuity per vehicle)
  4. Submit the Fabric transaction with the Merkle root + chain link
  5. Update `vehicle_ledger_anchor_state` with new chain tip and increment anchor count
  6. Mark the job complete in `vehicle_ledger_jobs` with the Fabric tx ID

### Task 6 — Compliance Panel SSE Endpoint
**File:** `src/routes/api/v1/dashboard/compliance-stream/+server.ts`

- Stream Server-Sent Events to the compliance dashboard
- Read from `vehicle_ledger_jobs` and `org_vt_snapshots`
- Each event payload must include:
  - `verified_anchor_count` (confirmed Fabric writes)
  - `raw_ping_count` (total pings ingested)
  - `days_since_first_ping`
  - `subscription_status`
- Render the upgrade gate when:
  - `ledger_anchor_count >= 500` AND
  - `days_since_first_ping >= 28` AND
  - `subscription_status !== 'active'`
- Upgrade gate must trigger M-Pesa STK push initiation flow

### Task 7 — Genesis Automation
**File:** `src/lib/server/ledger/genesis.ts`

Wire these four steps **synchronously** inside the batch ingest handler when `trigger_reason === 'genesis'`:

1. Cancel any active onboarding nudge for the vehicle/org
2. Fire a PostHog `genesis_anchor_created` event with vehicle and org metadata
3. Seed the initial `vehicle_ledger_anchor_state` row (position, timestamp, hash chain origin)
4. Enqueue a `GENESIS_ENROLLMENT` job in `vehicle_ledger_jobs`

**Timing constraint:** All four steps must complete within 2 seconds of the first batch ACK.
